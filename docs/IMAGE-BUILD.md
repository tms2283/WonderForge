# Reproducible Raspberry Pi Image-Build Handoff

## Status: experimental, not a verified bootable image

The codebase includes `image/wonderforge-pi4.yaml`, `image/layer/wonderforge-maker.yaml`, a `customize.overlay` staging recipe generated by `image/build-image.sh`, and a first-boot `systemd` application-staging unit. The upstream builder is [Raspberry Pi's official rpi-image-gen](https://github.com/raspberrypi/rpi-image-gen), pinned in the script to an identified November 2026 revision. The developer documentation describes custom device classes, layers, packages, overlays and `-S` source directories. [Official docs](https://raspberrypi.github.io/rpi-image-gen/).

**This ChatGPT container cannot build or test an actual ARM64 image.** Its host is x86_64 and it lacks the Linux `CAP_SYS_ADMIN`/mount namespace capabilities required by the official builder's `mmdebstrap` workflow. The official README confirms that those mount permissions and an ARM64 Raspberry Pi OS native host are the supported path. We have syntax-checked the supplied YAML and scripts, but have not run `rpi-image-gen build`, flashed a card, or confirmed the desktop/login behavior.

The recommended solution for the children's daily machine is therefore **official Raspberry Pi OS Desktop + the tested WonderForge `.deb` or source installer**, on a spare medium. The following is a useful, but experimental, image automation handoff for a proper build host.

## Image configuration

The recipe chooses `device.layer: rpi4`, `image.layer: image-rpios`, base `trixie-minbase`, and a custom `wonderforge-maker` layer. It allocates approximately 384 MB boot and 10 GB root partitions and requests known educational software, Chromium, Labwc/LightDM and the Raspberry Pi desktop meta-package. It may need adaptation to an exact pinned package snapshot or the official Raspberry Pi repository configuration before the build succeeds. **The desktop metapackage and first login are particularly important to validate; an image can finish assembly yet boot into an unusable login.**

The custom layer is designed to place a copy of the software, resources, game mod, installation and security scripts under `/opt/wonderforge-preinstall/`, plus a first-boot **app-staging** service. v0.5's first-boot script **does not create accounts or passwords**. It only copies the root-owned application payload into `/opt/wonderforge/` and records `/var/lib/wonderforge/staged`. An adult must first complete the official Raspberry Pi OS administrator login/setup, and then explicitly run the guarded installer with `--apply --admin-user=ADULT_USERNAME` to create the two locked child accounts and shared directory. The design never embeds a factory child password or a secret API key.

## Native host procedure

Use a spare Raspberry Pi 4B/5 or native ARM64 Debian Trixie build host with at least 12 GB free (larger recommended), installed development prerequisites and a second storage medium. Do **not** perform the build on the children's only working card. First preview:

```bash
bash image/build-image.sh
```

Install dependencies for the upstream builder as instructed by its documentation, and then attempt:

```bash
bash image/build-image.sh --build
```

The script clones the official upstream repository, checks out a pinned full commit, assembles an external `-S` project containing the layer and overlay, runs the upstream layer metadata lint and configuration resolver, and invokes the build. Output images, if any, belong under the upstream build's `work/` tree. The script itself does not flash or format an SD card. A failing lint, missing desktop package, disk full or unsuitable host is an unsuccessful build, not a reason to copy an incomplete `.img` to the children.

## Mandatory gates before flashing

1. **Adult-user provisioning:** verify that the image can create an adult administrator without requiring a published default password. The provided recipe intentionally does **not** invent this step. A raw image's compatibility with Raspberry Pi Imager OS customization must be established separately; do not assume custom `.img` images always honor the same customization hooks as official OS images.
2. **Actual boot:** write to a spare medium only, identify the device correctly in Raspberry Pi Imager, boot on the real Pi 4B, and confirm firmware, screen, keyboard, storage and login.
3. **First-boot staging:** inspect `journalctl -u wonderforge-firstboot.service`, confirm `/var/lib/wonderforge/staged`, finish adult-admin OS setup, run the explicit guarded account provisioner and set child passwords from the real adult-admin session.
4. **Security:** disable auto-login, validate home permissions and actual Unix identity, review firewall default, confirm system has no unapproved open network listener.
5. **Apps:** launch Chromium, Luanti and Thonny on real hardware. Confirm sound and accelerated graphics, then shut down and reboot.
6. **Persistence:** save a notebook and a Luanti world state, reboot and verify them.
7. **Performance:** check idle RAM, active desktop RAM, Luanti at 720p, time to load, FPS and thermal throttling. Never use unmeasured claims such as 60 FPS everywhere.
8. **Recovery:** remove the experimental card and prove the old card still boots. Verify full restore procedure for project data.
9. **Versioning:** record upstream Git SHA, apt package list, reproducible build logs, image SHA256, media size, board firmware and date, then freeze that as a tested configuration.

Do not publish an image as "fully automatic" without satisfying these gates. This handoff is intended to accelerate that final stage, not disguise it.
